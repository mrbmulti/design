CPC Document Publisher — Design Brief

Application: cpc_github_doc_publisher.py (Python 3.10+, Tkinter). Published title: GitHub Document Publisher and Index.

1. Purpose

The Document Publisher turns a local folder of articles into a set of GitHub Pages sites plus one automatically generated index (catalogue) site. You keep working in plain folders with HTML or Markdown pages. The app builds a local copy of the final website, lets you preview it, and uploads it to GitHub without a GitHub CLI login.

Goals:

  • One source directory holds everything; each subfolder is its own GitHub repository.
  • The index repository is built automatically from the articles, using your own template.
  • Nothing is uploaded unless a repository is explicitly switched on.
  • Account settings and the token stay in the source directory and are never published.

2. Key concepts

ConceptMeaning
Source directoryThe holding area you point the app at. It is never published itself.
Repository directoryAny immediate subfolder with an output.json. Each becomes one GitHub repository.
output.jsonEnables a directory and holds its record: name, description, category, repo name, owner, publish_settings, page_settings, progress.
record.jsonThe disabled form. Disabling renames output.json to record.json; enabling renames it back.
Index repositoryThe subfolder named exactly index. It is always the catalogue and is listed first.
templatesA folder in the source root, the only place templates are looked for.
account.privJSON file in the source directory holding the GitHub token (never uploaded).
Web folderGenerated output, one folder per repository. Must be separate from the source directory.

3. Source directory layout

source/
  account.priv            token (never published)
  templates/              optional page templates
  index/                  the catalogue repository
    index.html            index template (or named in output.json)
    output.json
    images/ (icon, logo)
  my-article/             one repository
    index.html or index.md
    other pages (.html / .md)
    images/ (splash, icon)
    output.json

A directory that arrives with an index.html or index.md and neither output.json nor record.json is given an output.json automatically, with publish switched off. The record is filled from the page title, the description meta tag and the files present.

4. How it is used

  1. Config tab. Set the source directory, the generated web folder (defaults to web beside the program), the preview directory, the local server port (default 8181), the GitHub token and the current GitHub account.
  2. Sources tab. Lists every subfolder with its state: Enabled, Disabled or Not configured. Select one or several rows and use Enable directory, Disable directory, Publish ON or Publish OFF (also on right-click). Publish ON enables the directory and sets the upload flag.
  3. Files and Repository tabs. Browse the real folders. Right-click to open in Explorer, view, edit, copy, paste, copy to root, or delete (which moves the item to the source root, not to the bin). Editing an output.json opens a field form (name, description, repository, account, template, publish) with an Edit as text fallback. The Published as column shows where each file lands or why it does not.
  4. Preview tab. Build creates the local website. Preview repository starts a local server on 127.0.0.1 and opens the chosen repository in the browser. Open shows the folder; Delete removes it after a safety check.
  5. GitHub tab. Upload to GitHub Pages shows a confirmation listing what will and will not be uploaded. Open GitHub Pages and Open GitHub go to the selected repository. Files report writes an HTML list of every file to be uploaded, per repository.
  6. Log tab. Shows every step; problems are written as ALERT lines and the work carries on.

Other tabs: Notes (help text from cpc_github_publisher.en.txt) and UI Choices (shared UI settings).

5. How a build works

Build (build_web_site) always works from a fresh temporary stage and only replaces the web folder once the whole site is ready, so a failed build never leaves a half-empty site.

For each enabled article directory:

  • Publishable files are copied as they are. Python, EXE, JSON settings, hidden files, skipped folders (.git, .venv, __pycache__, node_modules and similar) and symbolic links are never published.
  • Markdown is converted to HTML by the built-in converter; local .md links are rewritten to .html.
  • Existing HTML is left intact; only the article navigation (a link back to the index, plus links to the other pages) and a favicon are added.
  • If the record names a template (page_settings.template), the page body is placed into the template at {{CONTENT}}. A missing template raises an alert and the page is published as it is.
  • A .nojekyll file is added.

Template placeholders for article pages: {{CONTENT}}, {{TITLE}}, {{NAME}}, {{APP_NAME}}, {{DESCRIPTION}}, {{VERSION}}, {{CATEGORY}}, {{REPOSITORY}}, {{GITHUB_ACCOUNT}}.

6. How the index is generated

The index page comes from the index directory: the template named in its output.json, otherwise its own index.html. Two template styles are supported.

Placeholder template (used when the file contains {{APPLICATION_CARDS}}, as in portfolio-index.html):

PlaceholderValue
{{PORTFOLIO_NAME}}Index output.json name, else the Config site title, else "index". A name containing {{ is ignored.
{{PORTFOLIO_INTRO_HTML}}, {{HAS_INTRO}}Index output.json description, rendered from Markdown.
{{LOGO}}The icon or logo image in the index folder or its images folder.
{{INDEX_URL}}./
{{APP_COUNT}}, {{YEAR}}Number of articles, current year.
{{APPLICATION_CARDS}}One card per article.
{{QUICK_INDEX_HTML}}Currently empty.

Blocks written as {{#NAME}} ... {{/NAME}} are kept only when NAME has a value. The template is scanned once, so article text can never be mistaken for a placeholder.

Each card holds the title (linking to the article), category, splash image, description and links to the article's extra pages. The template's own script supplies search, category chips and the menu drawer. Colours, fonts and site wording live in the template, not in the program.

Block template (older style): <!--article--> ... <!--/article--> repeated per article with {{TITLE}}, {{DESCRIPTION}}, {{URL}}, {{SPLASH}}, {{ICON}}, and an inner <!--page--> ... <!--/page--> for extra pages. Still supported unchanged.

Article links in the index are relative (../repo-name/), which works because every repository is published on the same account.

7. How upload works

Upload first builds the whole local site, then plans each repository:

ConditionResult
Publish flag on, token presentUploaded
Publish flag offNot uploaded (logged)
No output.jsonAlert, not uploaded
No token in account.privAlert, not uploaded

For each repository that is uploaded:

  1. The token is checked against the GitHub API; a rejected token is reported and recorded.
  2. The repository is created if missing (public).
  3. It is cloned using the token, with no stored credentials and no CLI login.
  4. The built site is copied into /docs. A manifest records the files written, so files removed from the source are also removed on the next upload.
  5. Changes are committed and pushed. If nothing changed, nothing is committed.
  6. GitHub Pages is set to serve the /docs folder.
  7. Progress and the uploaded file list are written back into that directory's output.json.

A failure in one repository is logged and recorded without stopping the others. A confirmation dialog is shown before any upload starts.

9. Design rules in force

  • The source directory is never published and never modified by a build.
  • The index repository is always called index; each source subfolder is its own repository.
  • Templates are found only in the templates folder of the source root; there is no setting for another location.
  • No CSS or site title is written in the code; both come from templates, records or Config.
  • A missing item produces an alert in the log and the work carries on.
  • The publish flag is the only thing that allows an upload; without it the app only builds locally.
  • Existing records are never recreated over: a malformed output.json is shown and not overwritten.

10. Known points to decide

  • The index template's menu links to quick_index.html, which is not generated, and {{QUICK_INDEX_HTML}} is empty.
  • New records default to the category "Utilities", so uncategorised articles show that on the index cards.
  • Upload sends all repositories to the account of the single token in account.priv. The record's owner field is used for the GitHub tab links and filtering, not to pick a token.
  • Cards use the template's default colour; per-category colours are not generated.
  • A name read from the index template's <title> may be stored as the index record name; it is ignored while it contains a placeholder.
